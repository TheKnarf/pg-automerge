[CloudNativePG](https://cloudnative-pg.io) (CNPG) can add an extension to a
cluster without a custom PostgreSQL image. The extension ships as a small
image that holds only its files. The operator mounts that image read-only
into every instance pod and points PostgreSQL at it. CNPG calls these
*image volume extensions*. The repository builds such an image next to
the full [Docker](./docker.mdx) image, from the same compile:

| Image | What it is | For |
|---|---|---|
| `pg-automerge:<version>` | the official `postgres:18` image plus the extension | `docker run`, compose, local development, small deployments |
| `pg-automerge-cnpg:<version>-18-trixie` | the extension's files only, `FROM scratch` (it cannot be run) | a CNPG `Cluster`'s `spec.postgresql.extensions` |

```sh
mise run docker-build        # both images
mise run docker-build-cnpg   # only pg-automerge-cnpg:0.3.0-18-trixie
mise run cnpg-smoke          # build it, then test it in CNPG's PostgreSQL image (no Kubernetes)
mise run cnpg-e2e            # build it, then test it with the CNPG operator on kind
```

The name and tag follow CNPG's own extension images (`<extension version>-<PostgreSQL major>-<Debian release>`,
as in `pgvector:0.8.6-18-trixie`). The image has a repository of its own, so its
tags never get mixed up with the runnable image's.

## Requirements

- **CloudNativePG 1.27 or later** (`spec.postgresql.extensions`). Defining
  the extension in an image catalog needs 1.29 or later.
- **Kubernetes with image volumes**: on by default from Kubernetes 1.35, and
  stable from 1.36. On 1.33 and 1.34, enable the `ImageVolume` feature gate.
  The nodes need containerd 2.1 or later, or CRI-O 1.31 or later. On a
  managed service this depends on the provider's node images.
- **A PostgreSQL 18 operand on Debian trixie, amd64 or arm64**, for example
  `ghcr.io/cloudnative-pg/postgresql:18-minimal-trixie` or
  `18-standard-trixie`. Both variants share one base, and the library
  needs only `libc` and `libgcc_s`. The extension image must match the
  cluster's PostgreSQL major version, Debian release and CPU architecture.

**No bookworm.** A `-bookworm` operand cannot load the library: it is
built on trixie, and needs `GLIBC_2.38`, which bookworm's glibc 2.36 does
not have. `CREATE EXTENSION` fails with `version 'GLIBC_2.38' not found`.
The image is not built for bookworm either: the builder installs Rust
with Debian's `rustup` package, which bookworm does not have. Debian 12
also reached its end of life in June 2026, and CNPG supports its bookworm
images on a best-effort basis only.

## A cluster with pg_automerge

Push the image to a registry your cluster can pull from (see
[publishing](../operations/docker-ci.mdx#publishing-the-image)), then
list it in the `Cluster`. A `Database` resource can create the extension
for you:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: automerge
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:18-minimal-trixie   # trixie, like the extension image
  storage:
    size: 10Gi
  postgresql:
    parameters:
      pg_automerge.max_load_memory: "1GB"     # optional; see Configuration
    extensions:
      - name: pg-automerge                    # mounted at /extensions/pg-automerge
        image:
          reference: ghcr.io/you/pg-automerge-cnpg:0.3.0-18-trixie
---
apiVersion: postgresql.cnpg.io/v1
kind: Database
metadata:
  name: automerge-app
spec:
  name: app
  owner: app
  cluster:
    name: automerge
  extensions:
    - name: pg_automerge                      # the SQL name
      version: "0.3.0"
```

For each entry, the operator adds an image volume and mounts it at
`/extensions/<name>`. It also appends that path to two settings:

```
extension_control_path = '$system:/extensions/pg-automerge/share'
dynamic_library_path   = '$libdir:/extensions/pg-automerge/lib'
```

PostgreSQL 18 finds `pg_automerge.control` and the SQL scripts through the
first setting. It finds `pg_automerge.so` through the second, because the
control file names the library without a directory
(`module_pathname = 'pg_automerge'`). The extension needs no
`shared_preload_libraries`.

Mounting the image only makes the extension *available*. The `Database`
resource above runs `CREATE EXTENSION pg_automerge` as the superuser (it
is not trusted, see [Install](./install.mdx)). Without it, a superuser
can run that command, for example through `kubectl cnpg psql automerge -- -d app`.
The `app` owner cannot. To check that the image was resolved:

```sh
kubectl get cluster automerge -o jsonpath='{.status.pgDataImageInfo.extensions}'
```

The settings of [Configuration](../reference/configuration.mdx) go in
`spec.postgresql.parameters`. CNPG accepts custom names with a dot, and a
value set before the library loads applies once it loads. Size
`pg_automerge.max_load_memory` to the pod's memory limit, as for a
container ([Sizing memory](../operations/index.mdx#sizing-memory)).

Pick the `name` once (`pg-automerge` above) and keep it. Renaming it moves
the mount, which triggers a rolling update.

**On kind** (or any cluster), you can use a locally built image without a
registry. Run `kind load docker-image pg-automerge-cnpg:0.3.0-18-trixie`
and set `pullPolicy: IfNotPresent` (already the default for any tag but
`latest`) or `Never` on the image. `tests/cnpg_e2e.sh` does exactly that.

## Updating

1. Change `extensions[].image.reference` to the new tag. CNPG restarts the
   instances one by one (image volumes are resolved when a pod starts).
   Every image holds all the upgrade scripts, so any older version can
   update.
2. Bump `version` in the `Database` resource. The operator then runs
   `ALTER EXTENSION pg_automerge UPDATE TO '<version>'`. Without a
   `Database` resource, run `ALTER EXTENSION pg_automerge UPDATE` as a
   superuser in every database that has the extension.

Between the two steps the new library serves the old SQL definitions,
exactly as after recreating a container ([Updating](./updating.mdx)). The
[Changelog](../changelog.mdx) says whether a version needs more.

To remove the extension, first set `ensure: absent` in the `Database`
resource (or run `DROP EXTENSION`), then delete the `extensions` entry,
which triggers a rolling update.

## What is tested

`tests/cnpg_smoke.sh` (`mise run cnpg-smoke`, and part of
`mise run docker-test` and the CI `docker` job) needs no Kubernetes. It
runs CNPG's pinned `18-minimal-trixie` operand image, mounts the extension
image read-only at `/extensions/pg-automerge` (a Docker image mount,
which is what an image volume is), and sets the two settings exactly as
the operator writes them. It checks:

- the image's labels and that it holds exactly CNPG's layout:
  `/lib/pg_automerge.so`, the control file and SQL scripts in
  `/share/extension`, and the license in `/licenses/pg_automerge`;
- that the operand has no copy of its own;
- that `CREATE EXTENSION` works for the superuser and is refused for a
  plain role;
- that the backend maps the library from the mount, and that a setting
  given before the library loads applies;
- merges, jsonb reads with a GIN index, `automerge_spans` and the upgrade
  path;
- that the server log shows no crash.

`tests/cnpg_e2e.sh` (`mise run cnpg-e2e`, and the CI `cnpg-e2e` job on
the image the `docker` job built) covers the operator itself. It takes a
few minutes and needs kind, so it is not part of `mise run ci` or
`docker-test`. It creates a throwaway kind cluster (pinned kind and
Kubernetes 1.36 node image), installs the pinned CNPG release (1.30.1),
loads the images into the node (`kind load`, `pullPolicy: Never`, no
registry), and walks the steps of this page:

1. A `Cluster` on the same pinned operand, with an *older* extension
   image in `spec.postgresql.extensions`: the image under test with the
   previous release's SQL scripts and `default_version`, standing in for
   that release's image. It checks the pod's image volume and
   `status.pgDataImageInfo`, the two settings, the
   `pg_automerge.max_load_memory` parameter, and that the `app` owner
   cannot `CREATE EXTENSION`.
2. A `Database` resource with that older `version`: the operator creates
   the extension. Data is written, and the backend maps the library from
   `/extensions/pg-automerge/lib`.
3. The `Cluster`'s image changed to the image under test: the pod rolls
   (a new pod with the new image volume), the data survives, and the
   catalog stays at the old version with the update path found.
4. The `Database`'s `version` bumped: the operator runs
   `ALTER EXTENSION ... UPDATE TO`. Then merges, jsonb reads with a GIN
   index, `automerge_spans` and `automerge_memory_usage()` on the regress
   fixtures.
5. Removal as described above: `ensure: absent` drops the extension, and
   deleting the `extensions` entry rolls the pod without the image
   volume. The server log shows no crash.

kind's node runs as root of the Docker daemon, so its inotify instances
count against root's `fs.inotify.max_user_instances`. kind asks for 512,
and Debian's default is 128. Where root already uses most of them (a k3s
on the same host, for example), kube-proxy and the operator crash-loop
with `too many open files`, and the test prints that diagnosis. Raise the
limit (`sudo sysctl -w fs.inotify.max_user_instances=512`), or run kind on
a rootless Docker daemon of your own user, whose containers count against
your user instead. `CNPG_E2E_DOCKER_HOST` points the test at it; the
images are still built by the default daemon:

```sh
dockerd-rootless.sh --data-root ~/.local/share/docker-e2e \
  -H unix://$XDG_RUNTIME_DIR/e2e/docker.sock &
CNPG_E2E_DOCKER_HOST=unix://$XDG_RUNTIME_DIR/e2e/docker.sock mise run cnpg-e2e
```

Neither test covers more than one instance (replicas, switchover), image
catalogs, or a managed Kubernetes service.
[Docker image](../design/docker-image.mdx#cloudnativepg-extension-image)
has the packaging decisions.
